START HERE

In this guide, AI-native means that an AI capability is central to how a product delivers its core outcome. AI-native SDLC means designing software delivery around human intent, machine-actionable context, bounded agent work, and verifiable evidence. These are working definitions; industry usage varies.

CONVENTIONAL

People drive the workflow.

A shopper filters a catalog, compares products, and builds a cart. Rules and software execute predefined operations.

AI removed? The core experience is unchanged.

EMBEDDED AI

AI improves a step.

The same store adds generated product summaries or a review sentiment feature. AI augments an established flow.

AI removed? The store still delivers essentially the same outcome.

AI-NATIVE

Intent shapes the workflow.

“Plan a camping kit under ₹12,000.” The store clarifies constraints, finds compatible gear, and proposes an editable bundle.

AI removed? The core promise needs redesign.

Separate the axes.

An AI-native store can be built manually. A conventional store can be built using an AI-native SDLC. The product’s intelligence and the team’s delivery method are separate design choices.

Grounding ≠ instruction authority

A retrieved document may contain “ignore the rules.” Treat it as untrusted content. Separate instructions from data, constrain tools, validate outputs, and verify authorization at execution. Prompt wording alone is not a security boundary.

LESSON 04 · REPOSITORY AS AN INTERFACE

Give the agent a workshop.
Not just a prompt.

A useful coding environment has explicit instructions, reusable procedures, constrained tools, executable contracts, and observable results.

AGENT

The executor

A model-driven process that selects actions, uses tools, and responds to observations within a defined scope. It needs a task, permissions, completion criteria, and stop conditions.

SKILL

The procedure

Reusable task instructions with examples or scripts: for example, “add a database migration safely.” A skill describes how to work; it does not grant credentials or bypass policy.

MCP

The connection

Model Context Protocol connects an AI host through clients to servers exposing tools, resources, and prompts. It standardizes integration; application code still owns permissions and approvals.

Terminology: this guide uses MCP (Model Context Protocol), likely the intended “MCS” in the topic list. A project-specific MCS should be defined separately.

AI host→MCP client⇄MCP server→Authorized service

LESSON 05 · CONTROLLED AUTONOMY

An agent is a loop.
Engineering gives it limits.

A workflow follows predefined transitions. An agent chooses its next step from observations. Both need a reliable execution harness.

Observe→Propose→Validate→Act→Verify ↻

The inner loop: do the task

Assemble context, choose a tool, check scope and budget, execute, inspect the result, and decide whether to continue. Stop on success, cancellation, uncertainty, repeated failure, or a hard limit.

The outer loop: improve the system

Collect consented, redacted failure evidence. Turn it into regression cases. Change the spec, context, tool, model, or harness. Evaluate against a frozen baseline before release. Do not let feedback silently rewrite production behavior.

LESSON 06 · HUMAN CONTROL

Make intelligence useful.
Make its limits visible.

An AI-native experience does not have to be a chat window. Combine language for intent with structured interfaces for inspection and control.

Design the entire uncertainty journey

  1. Capture intent: ask only for constraints that change the result. Offer editable chips for budget, size and exclusions.
  2. Show grounded progress: “Checking current stock” describes a real operation. Avoid invented percentages.
  3. Present evidence: show product sources, limitations, timestamps and assumptions. Never invent a calibrated confidence score.
  4. Preview the effect: display exact items, quantity, total, shipping and return terms before confirmation.
  5. Give control: edit, cancel, choose a conventional flow, or escalate to a person. Support keyboard and screen-reader use.
  6. Handle recovery: preserve confirmed intent, explain partial failure, and distinguish “request sent” from “order confirmed.”

Design states before designing sparkle

Suggest → inspect

Separate recommendation from commitment. Let a shopper see why a bundle fits and replace any item. Explain observable evidence and assumptions, not private model reasoning.

Confirm → commit

Bind consent to the displayed quote. Keep payment and address entry in secure, conventional components. Never imply that a generated confirmation proves a completed order.

Fail → recover

Offer catalog browsing when AI or retrieval fails. Keep the cart intact. Tell the user whether an operation failed, succeeded, or has an unknown result awaiting reconciliation.

REMEMBER THISIntent in language. Consequences in controls. Trust comes from inspectable behavior and effective recovery.
LESSON 07 · EVIDENCE BEFORE RELEASE

Passing tests is necessary.
It isn’t the whole argument.

Deterministic checks protect contracts. Evaluations measure variable behavior across representative tasks. Production signals reveal what your lab missed.

Where strict TDD fits in AI-native SDLC

TEST-DRIVEN DEVELOPMENT

AI-native SDLC can adopt strict TDD as an explicit engineering policy. It is not a universal requirement of the AI-native label. This guide recommends it for testable behavior changes in deterministic services, especially pricing, authorization, order state and retry handling. The coding agent follows the same discipline as an engineer: an observable failing test comes before the implementation that makes it pass.

01 / RED

Prove what is missing.

Derive one small behavioral test from an acceptance criterion. Run it against the current implementation and observe the expected failure. Investigate setup or infrastructure errors; they do not demonstrate the missing behavior.

02 / GREEN

Make that behavior work.

Write the minimum implementation needed to pass the test, then run the relevant existing suite. Do not delete assertions, skip the test, or change the expected outcome merely to turn the result green.

03 / REFACTOR

Improve the design safely.

Remove duplication and clarify responsibilities while keeping behavior unchanged and tests passing. Repeat for the next behavior. Writing all the code first and adding tests afterward is not strict TDD.

TDD cycle: Agile Alliance’s TDD definition. Agent verification and failure-first bug repair: Claude Code best practices. The adoption policy below is this guide’s recommendation.

Make the TDD policy enforceable for coding agents
  • Scope: declare which changes require red–green–refactor in the constitution, repository instructions and task contract. Define reviewed exceptions for exploration, documentation or visual-only changes, with an appropriate verification method.
  • Evidence: retain the acceptance ID, test name, exact command, expected failing output before the implementation, passing output afterward, and final regression results. A green CI result alone cannot prove tests were written first.
  • Independent judgment: review test intent against the requirement. An agent can generate a test and implementation that share the same misunderstanding. Use independent review, edge cases and, where useful, mutation testing to challenge assertions.
  • Test changes: an incorrect test may be corrected with a documented reason and review. Protect the agreed behavior; do not make every test file permanently uneditable.
  • Legacy code: use characterization tests to capture existing behavior before refactoring. Those may start green. A bug fix still needs a regression that demonstrates the faulty behavior before the repair.
TDD + evals.

Use deterministic tests for tool schemas, permission checks, business rules and orchestration. For variable model behavior, define evaluation cases, rubrics and a baseline before tuning; assess repeated trials and failure slices. Do not require exact wording from a live model when meaning or task success is the real contract. Mocked model responses make unit tests repeatable but do not establish live-model quality.

REMEMBER THISSpec defines the outcome. TDD drives the code. Evals measure AI behavior. A passing suite still needs meaningful assertions and accountable review.
TESTS

Does the code obey?

Unit, integration, contract, concurrency and end-to-end tests cover authorization, totals, retries, stock and state transitions.

Example: ten retries create one order.

EVALS

Does the AI succeed?

Versioned scenarios and graders measure task success, grounding, tool choice, abstention and robustness across varied inputs.

Example: constrained bundles satisfy budget and compatibility.

OBSERVABILITY

Does it work in use?

Trace tool calls and releases; watch quality samples, latency, cost, failure rates and user corrections without collecting unnecessary private data.

Example: canary results compared with a control.

Build an evaluation set you can trust

Start with representative tasks and explicit expected outcomes. Include common requests, boundary cases, ambiguous intent, unavailable tools, stale evidence, adversarial content and tenant-isolation attempts. Keep a development set separate from a frozen release holdout. Record model, prompt, index, tools and grader versions.

Use exact checks where possible, rubric-based model judges where helpful, and human review for ambiguous outcomes. Calibrate judges against human labels and inspect disagreements. Repeat stochastic cases and report sample counts, variation and failures by slice; a single aggregate score hides important defects.

    • Use typed public interfaces and runtime validation at every external boundary. Deny by default and validate tenant identity server-side.

    LESSON 10 · PRODUCTION FEEDBACK

    Every production failure
    should teach the system.

    Contain harm, establish facts, reproduce the failure, repair the correct layer, and preserve a regression. An agent can help investigate; incident authority stays explicit.

    Worked bug fix: the duplicate-order race

    AC-04 → INC-042 → REGRESSION

    A provider accepts a payment-intent request, but the response times out. A retry enters a second application worker. An in-memory “already processed” map does not protect across workers or restarts. A new idempotency key on each attempt makes the retry look like a new purchase.

    A local database transaction cannot atomically commit with a remote payment provider. Use durable idempotency, an outbox, provider-side keys, webhook deduplication and reconciliation. Check provider key-retention behavior and handle unknown outcomes before retrying outside that window.

    Incident policy: what the agent can and cannot do

    Allow scoped, redacted log analysis, candidate reproduction tests, diff proposals and impact summaries. The incident commander owns severity, containment and customer communication. Separate approval is required by this example policy for production writes, replay of payments, refunds or deployment. Use audited, time-limited incident access.

    For an urgent fix, allow a smaller artifact set with an incident ID, scoped change, critical regression evidence, reviewer, rollout and rollback. Backfill the full spec and postmortem promptly under a named owner and deadline. “Emergency” does not mean “unreviewed.”

    REMEMBER THISContain → reproduce → repair → prove → release → learn. Fix the code and the condition that let it escape.

    Document the release bundle

    Record code commit, spec revision, model/provider configuration, prompt version, retrieval corpus/index version, tool schemas, policy version, evaluation dataset/grader version, and rollback target. A prompt-only change is still a behavior change.

    Make exceptions expire

    Record the rule being waived, rationale, approving owner, scope, compensating controls, expiry and follow-up task. A waiver cannot secretly expand itself into permanent agent authority.

    A PRACTICAL STARTING SEQUENCE
    01 / BASELINE

    Choose a bounded slice

    Pick one feature with a measurable outcome and low blast radius. Record current lead time, review effort, escaped defects and task quality. Decide who owns the result.

    02 / INSTRUMENT

    Make it actionable

    Write the spec, context map, task contracts and repository instructions. Add tests and a small representative eval set before increasing autonomy.

    03 / LEARN

    Review the evidence

    Compare delivery time and quality with the baseline, including rework and operational costs. Expand scope only when evidence supports it. Preserve failures as regression cases.
